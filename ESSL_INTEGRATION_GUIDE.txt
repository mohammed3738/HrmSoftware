--------------------------------------------------------------------------------
  0.1  WHAT THIS GIVES YOU
--------------------------------------------------------------------------------

Today attendance reaches the HRMS as an Excel file somebody uploads. After
this, the punches come straight from the eSSL biometric machine and the HRMS
fills in each employee's in-time and out-time by itself, every two hours,
including for night-shift staff whose duty crosses midnight.

Nothing about the Attendance List, Attendance Register, payroll or leave
balance changes. They read the same Attendance rows they always did; only
the way those rows get their in/out times is new.

The Excel upload keeps working. During changeover you can run both: a day
whose times came from an upload is marked as manual, and the sync leaves it
alone, so the two cannot fight over the same day.

--------------------------------------------------------------------------------
  0.6  IF SOMETHING GOES WRONG
--------------------------------------------------------------------------------

Three properties of the design mean nothing is ever stuck:

  Punches are never rewritten. They are stored exactly as the device
  recorded them, separately from the attendance. The rules can be
  re-applied over any date range at any time, with nothing fetched again --
  that is the "Rebuild from stored punches" button.

  A failed push loses nothing. The agent only moves a target's resume point
  after that target has accepted the punches, so the next run re-sends
  whatever did not land, however long the gap.

  Manual decisions win. An approved correction or an Excel upload marks the
  day, and the sync skips it.

Part 12 lists every failure we know of, with what each one actually means.
Part 14.6 removes the whole thing again if you decide against it.

================================================================================
  PART 1 -- HOW IT WORKS
================================================================================
================================================================================

--------------------------------------------------------------------------------
  1.1  WHY THE TRAFFIC FLOWS OUTWARD
--------------------------------------------------------------------------------

The obvious design would be for the HRMS to connect to SQL Server and read
dbo.DeviceLogs itself. From the Ubuntu server that cannot work:

  * No route. The Ubuntu server is on network A. 192.168.1.135 is private to
    network B. Only RDP (port 83) is published from network B, and that is a
    remote-desktop port, not a database one.

  * Exposing SQL Server to the internet to get around that would be the
    wrong trade. Port 1433 open to the world, on a SQL Express instance that
    is probably not patched monthly, next to every employee's biometric
    data.

So the traffic runs the other way. A small Python script -- the agent --
runs ON the Windows server, where SQL Server is local and the
authentication problem disappears. It reads the punches and POSTs them to
the HRMS over ordinary outbound HTTPS, which needs no inbound firewall rule
on network B at all.


--------------------------------------------------------------------------------
  1.2  THE SHAPE OF IT
--------------------------------------------------------------------------------

      Windows server (network B)                 HRMS (network A)
      --------------------------                 ----------------
      eSSL devices
           |
           | punches
           v
      eTimeTrackLite  --->  SQL Server           Django + Celery
                            eTimetracklite1           |
                                 ^                    |
                                 | local SELECT       | POST
                                 | (part 4)           |  /api/biometric/punches/
                                 |                    |  X-HRMS-Sync-Token
                                 |                    |
                            essl_punch_agent.py ------+  outbound HTTPS 443
                            Scheduled Task,              (nothing inbound
                            every 30 minutes              on network B)

      Then, on the HRMS, every two hours:
          stored punches  --(the rules, part 2)-->  Attendance in/out times


--------------------------------------------------------------------------------
  1.3  PUNCHES AND ATTENDANCE ARE KEPT APART
--------------------------------------------------------------------------------

Two things happen on the HRMS, and the split matters:

  1. The punches are stored exactly as the device recorded them, in a new
     table (website_biometricpunch). This is the audit trail. It is never
     rewritten.

  2. In-time and out-time are derived from those punches by the rules in
     part 2, and written to the existing Attendance table -- the same rows
     everything else already reads.

Because the raw punches are kept, the rules can be re-applied at any time
without going back to the punch machine. That is what makes a mistake --
a wrong night-shift tick, an employee code that did not match -- a
five-second fix rather than a data recovery exercise.


--------------------------------------------------------------------------------
  1.4  ONE AGENT, SEVERAL HRMS SERVERS
--------------------------------------------------------------------------------

The agent's configuration has one [hrms:<name>] section per destination,
each with its own token and its own resume point. That is exactly what the
three stages need: point it at the development PC first, add the Ubuntu
staging copy next, add the live HRMS last, and turn the earlier ones off as
you move on. During a changeover it can feed two at once, which is how you
compare them.

A destination that is down, or whose token is wrong, is skipped and retried
on the next run. It never holds up the others, and it never loses punches:
a destination's resume point only moves forward after it has accepted them.


================================================================================
================================================================================
  PART 2 -- THE RULES THAT DECIDE IN-TIME AND OUT-TIME
================================================================================
================================================================================

These are pinned by 37 tests in hrms/website/tests/test_biometric_sync.py.
Run that file after any edit to the rules.

--------------------------------------------------------------------------------
  2.1  DAY SHIFT  (the default for everybody)
--------------------------------------------------------------------------------

  For a date D:

    in-time  = the FIRST punch of D -- but only while D has no in-time yet.
               Once set, it is never moved.

    out-time = the LAST punch of D, refreshed on every run. Somebody who
               punched out at 18:02 and again at 19:40 gets 19:40 as soon as
               the next run sees it.

  Example -- punches at 09:58, 13:30 and 19:02 on one day:

    the 10:00 run sees 09:58 and 13:30   ->  in 09:58, out 13:30
    the 20:00 run also sees 19:02        ->  in 09:58, out 19:02
    the 22:00 run sees nothing newer     ->  unchanged

  A punch that arrives late and is EARLIER than the stored out-time does not
  move it. Only a later punch does.

--------------------------------------------------------------------------------
  2.2  NIGHT SHIFT  (employees ticked "Night Shift")
--------------------------------------------------------------------------------

  For a date D, duty starts on D and ends on D+1:

    in-time  = the LAST punch of D
    out-time = the FIRST punch of D+1

  Worked example:

    23 Oct: punch 21:50                  ->  23 Oct in 21:50
    24 Oct: punches 06:05, 21:45
              23 Oct out = 06:05  (24 Oct's first punch)
              24 Oct in  = 21:45  (24 Oct's last punch)
    25 Oct: punch 06:10
              24 Oct out = 06:10

  So 23 Oct reads 21:50 -> 06:05 and 24 Oct reads 21:45 -> 06:10. Attendance
  already treats an out-time earlier than the in-time as an overnight shift,
  so the hours and the status come out right with no further change.

--------------------------------------------------------------------------------
  2.3  GUARD RAILS  (all configurable in hrms/.env)
--------------------------------------------------------------------------------

  BIOMETRIC_NIGHT_IN_FROM     default 12:00
      A night employee's in-time is the day's last punch only if it falls at
      or after this. Somebody who punched once, at 06:00, was punching OUT
      of the previous night -- that day gets no in-time rather than a
      nonsense one.

  BIOMETRIC_NIGHT_OUT_UNTIL   default 12:00
      The next day's first punch counts as the out-punch only before this.

  BIOMETRIC_MAX_SHIFT_HOURS   default 16
      A span longer than this is a missed out-punch, not a shift: the
      out-time is left blank, so the day shows as needing a correction
      instead of crediting 23 hours.

  An out-time already recorded is never blanked just because a later run
  could not derive one. That would turn a complete day back into a missing
  punch.

  BIOMETRIC_FUTURE_PUNCH_TOLERANCE_DAYS   default 1
      A punch dated further ahead than today plus this many days is
      rejected outright rather than stored. A punch in the future means a
      reader's clock is wrong, not that somebody worked -- this
      installation's history contains one dated 31 December. Storing it
      would build an attendance row on a day nobody has worked yet, which
      is easy to miss and awkward to unpick afterwards. Rejections are
      counted in the run's message on the Biometric Sync page.

--------------------------------------------------------------------------------
  2.4  WHO COUNTS AS NIGHT SHIFT
--------------------------------------------------------------------------------

  THE SHIFT ROSTER DECIDES, wherever it covers the date. That is the whole
  point of rostering: night duty rotates, so who is on nights changes week to
  week, and a standing tick on the employee cannot express that. The tick on
  the employee form is only the fallback, for staff who are permanently on
  nights and never appear in the roster.

  Within a roster entry, the checks run most-definite first:

  1. ITS OWN "NIGHT SHIFT" TICK. Attendance -> Shift Roster, on the entry
     itself. HR has said so outright, and nothing else is consulted. This is
     the one to use.

  2. TIMINGS THAT CROSS MIDNIGHT, e.g. 22:00 to 07:00. The entry says it
     itself, so no tick is needed.

  3. A NAME CONTAINING night / overnight / graveyard / nite. Best effort, for
     entries made before the tick existed. Do not rely on it: "B Shift" and
     "Shift 3" say nothing either way.

  4. ORDINARY DAYTIME TIMINGS, e.g. 09:00 to 18:00. A positive "not nights",
     and it overrides the employee's standing tick for those dates.

  An entry matching none of the four is no answer at all -- no tick, no
  timings, a neutral name. The next entry is tried, and then the employee's
  own setting. It is deliberately NOT read as a day shift: doing that would
  hand a permanently-night employee a nonsense in-time on the strength of a
  roster entry that never said anything.

  ARCHIVED ROSTER ENTRIES: it depends which kind.

    * ARCHIVED AUTOMATICALLY because the dates went by (part 9.4) -- STILL
      HONOURED for those dates. The entry is the true record of what the
      roster said, so recalculating an old night shift reaches the same
      answer it did at the time.

    * ARCHIVED BY HAND -- ignored entirely. That is this app's soft delete,
      and it means somebody judged the entry wrong, so it must not keep
      steering attendance.

  Then, only if the roster says nothing for that date:

  5. The "Night Shift" tick on the employee's own form.

  6. An employee whose Shift Start Time is after their Shift End Time.

    IF A ROSTERED NIGHT SHIFT IS COMING OUT WRONG, the usual cause is an
    entry that falls into the "no answer" case above -- a rotation named
    something neutral with the timings left blank. Open it in the Shift
    Roster and tick Night Shift. 12.19 has the check for it.

--------------------------------------------------------------------------------
  2.5  DAYS THE SYNC NEVER TOUCHES
--------------------------------------------------------------------------------

  * Days whose times were set by hand. Both paths that do this -- an
    approved Attendance Correction and an Excel upload -- mark the day, and
    the sync skips it. A human decision outranks the machine.
  * Days inside a FINALIZED payroll run. Payslips have gone out.
  * Days before the employee's date of joining.
  * Employees whose status is Left or Archived.

  Each is counted as "left alone" on the Biometric Sync page, so a day that
  did not move always has a stated reason.

  To override the manual-times rule deliberately, part 12.10 has --force.
  Nothing overrides a finalized payroll period, including --force.

--------------------------------------------------------------------------------
  2.6  WHEN THE HRMS RUNS THE RULES
--------------------------------------------------------------------------------

  BIOMETRIC_SYNC_HOURS, default: 10,12,14,16,18,20,22,0

  Every second hour from 10:00 through midnight. Each run re-reads the last
  BIOMETRIC_SYNC_LOOKBACK_DAYS days (default 3), so a punch written late to
  the device database still lands, and a night shift's second half is always
  inside the window. Two is the floor for that setting, because rebuilding
  23 Oct for a night employee needs 24 Oct's punches as well.

  NOTE ON THE REQUESTED SCHEDULE. "From 10:00 am till 12:00 with 2 hrs
  interval" read literally -- 10:00 to 12:00 noon -- is two runs a day, and
  would leave every evening punch unseen until the next morning. It is set
  up as 10:00 through 00:00 (midnight) at two-hour intervals instead, which
  is what a working day and a night shift need. Midnight is in the list on
  purpose: that run is what closes the previous night shift. If two runs a
  day really is what you want, set

      BIOMETRIC_SYNC_HOURS=10,12

  and restart celery-beat. Nothing else changes.

  The agent on the Windows server runs more often than this (every 30
  minutes) because pushing punches is cheap. The two-hourly job on the HRMS
  is what turns them into attendance.

================================================================================
  PART 3 -- HOW eSSL STORES PUNCHES
================================================================================
================================================================================

Taken from the eTimeTrackLite web application itself, so the integration is
built on what eSSL actually does rather than on a guess.

--------------------------------------------------------------------------------
  3.1  PUNCHES LIVE IN TWO PLACES, AND BOTH HAVE TO BE READ
--------------------------------------------------------------------------------

  A punch is one row per finger or card read:

      UserId                     the device's own identifier for the person
      LogDate                    datetime of the punch, to the second, local
      DeviceId                   which reader
      Direction / AttDirection   in/out, when the device reports one
      DeviceLogId                identity column

  It can be in either of two tables:

      dbo.DeviceLogs
          A buffer for punches just downloaded from the devices.
          eTimeTrackLite empties it as they are archived, so ON A TIDY
          INSTALLATION IT IS OFTEN COMPLETELY EMPTY. Its primary key is
          (DeviceLogId, UserId, LogDate).

      dbo.DeviceLogs_<month>_<year>
          One table per month -- DeviceLogs_10_2026, DeviceLogs_9_2026 and
          so on, around a hundred of them on this installation, going back
          to 2018. This is where the punches actually live. Their primary
          key is (UserId, LogDate) -- the punch identity itself -- which is
          what marks them as the real store rather than a loose copy.

  ONLY THE MONTHLY TABLES ARE READ. That is the default, and it is right for
  this installation: the punches are there, and the buffer is always empty.
  A month with no table yet is simply skipped, which is not an error -- it
  means that month has no punches.

  The buffer is not read, but it IS counted on every run. If it ever holds
  anything, the agent logs:

      WARNING: dbo.DeviceLogs holds 42 punch(es) that have not been archived
               yet, and read_devicelogs_buffer = no, so they are being
               skipped.

  Those punches are not lost -- they arrive as soon as eTimeTrackLite
  archives them, because the agent re-reads a window rather than only new
  rows. But if the warning keeps appearing, the buffer is not being emptied
  promptly and you should read it too:

      read_devicelogs_buffer = yes          in essl_agent.ini
      BIOMETRIC_MSSQL_READ_BUFFER=true      in hrms/.env, for --pull

  With that on, a punch found in both places is sent twice and
  de-duplicated by the HRMS, which keys on (UserId, LogDate) exactly as
  these tables do -- so the overlap costs nothing.

  The monthly tables are not byte-identical to dbo.DeviceLogs: they carry an
  UpdateFlag it lacks, and Direction is a different width. That is why the
  query names its columns instead of using SELECT *.

    A CORRECTION. Earlier versions of this guide said dbo.DeviceLogs was the
    only table to read, and that the monthly ones were touched only for
    maintenance. That was inferred from eTimeTrackLite's own code, which
    enumerates them with TABLE_NAME LIKE '%DeviceLogs_%', and it was wrong.
    A live installation showed dbo.DeviceLogs holding 0 punches while 220
    employees and a decade of history sat in the monthly tables. If you are
    on a version of the agent that reads only dbo.DeviceLogs, --test reports
    a healthy connection and 0 punches, and nothing ever syncs.

--------------------------------------------------------------------------------
  3.2  UserId IS NOT THE EMPLOYEE CODE
--------------------------------------------------------------------------------

  DeviceLogs.UserId matches Employees.EmployeeCodeInDevice, and
  Employees.EmployeeCode is the code HR uses. eTimeTrackLite's own
  vw_DeviceLogList view joins them exactly that way, and so does the agent
  -- so each punch arrives at the HRMS carrying the employee code a human
  recognises, not just a device number.

--------------------------------------------------------------------------------
  3.3  eSSL DELETES DUPLICATE PUNCHES
--------------------------------------------------------------------------------

  eTimeTrackLite has a routine that removes duplicates:

      delete FROM DeviceLogs WHERE DeviceLogId in (
          SELECT Min(b.DeviceLogId) FROM ... GROUP BY UserId, LogDate ...)

  Two things follow, and both shaped the design:

  1. DeviceLogId is NOT stable. A punch's id can disappear. So the HRMS
     never keys on it -- it is stored only so a punch can be traced back to
     eSSL for support.

  2. eSSL itself treats (UserId, LogDate) as the identity of a punch. The
     HRMS uses exactly the same identity for its unique constraint,
     (device_user_id, punch_date, punch_time). That is what makes re-sending
     an overlapping window free, which every run does on purpose.

--------------------------------------------------------------------------------
  3.4  WHY NOT dbo.AttendanceLogs
--------------------------------------------------------------------------------

  eTimeTrackLite keeps its own computed daily summary there (InTime,
  OutTime, Status, LateBy, PunchRecords...). It is tempting, but it applies
  eSSL's shift definitions, grace periods and half-day rules -- all
  configured separately from the HRMS, all free to drift from it, and none
  of them matching part 2. Reading the raw punches means the HRMS owns the
  policy and eSSL is only the sensor.

--------------------------------------------------------------------------------
  3.5  THINGS DELIBERATELY NOT USED
--------------------------------------------------------------------------------

  ParallelDatabaseDetails / eTimetrackParallelDBSync.exe is eSSL's built-in
  export to a second database. It cannot help here: it would need the Ubuntu
  PostgreSQL reachable from network B, which is the problem being avoided.

  The iclock/*.aspx endpoints (cdata, getrequest, devicecmd) are the ADMS
  push protocol the biometric devices use to talk to eTimeTrackLite.
  Pointing devices at anything else risks the attendance eSSL itself
  records, so the integration stays out of that path entirely.

================================================================================
  PART 4 -- CREDENTIALS: WHY NOTHING HAS TO BE CREATED
================================================================================
================================================================================

--------------------------------------------------------------------------------
  4.1  WHAT eTimeTrackLite ITSELF USES
--------------------------------------------------------------------------------

eTimeTrackLite stores its own database settings in a plain text file called
Settings.txt, in the same folder as the web application
(.../iclock/Settings.txt). It is six bare lines with no keys. On this
installation it reads:

    MS SQL Server                 database type
    WIN-5E3312PVO5J\SQLEXPRESS    server / instance
    eTimetracklite1               database
    Sql Server Authentication     authentication mode
    essl                          login name
    rKWYgQrTCGc=                  password, scrambled by eTimeTrackLite

Worth noting, because it contradicts a reasonable assumption: SSMS may well
connect with Windows Authentication, but eTimeTrackLite does not. It uses
SQL Server Authentication as the login `essl`. That login already exists and
already has access to this database.

The agent reads the first five lines of that file automatically, so you do
not have to retype the instance name or the database's exact spelling -- the
two things most often got wrong. Part 5.4 shows you what it found.

The password cannot be read back out of that file: it is scrambled with a
key held inside eTimeTrackLiteLibrary.dll. Run
eTimeTrackDatabaseSettings.exe, which ships beside eTimeTrackLite, to see or
re-set it.

--------------------------------------------------------------------------------
  4.2  THE TWO WAYS TO CONNECT -- BOTH CREATE NOTHING
--------------------------------------------------------------------------------

  OPTION A -- WINDOWS AUTHENTICATION            sql_auth = windows
  ----------------------------------------------------------------
  SQL Server trusts whichever Windows account the Scheduled Task runs as. No
  password is stored anywhere on disk, which is why this is the one to
  prefer. It works because the agent runs ON the Windows server; the account
  only has to be one SQL Server already accepts -- in practice, the account
  you already log in and use SSMS with.

  If SQL Server refuses that account, do not create a login for it. Either
  run the task as the account that does work, or use option B.

  OPTION B -- REUSE eTimeTrackLite's OWN LOGIN  sql_auth = sql
  ----------------------------------------------------------------
  Use the `essl` login from Settings.txt. This is an existing login, so
  nothing is created here either. You do need its password (4.1), and it
  then sits in essl_agent.ini -- which is why option A is better where it
  works.

  Leave sql_auth blank and the agent follows whatever Settings.txt reported,
  which on this installation means option B.

--------------------------------------------------------------------------------
  4.3  WHAT ABOUT A DEDICATED READ-ONLY LOGIN
--------------------------------------------------------------------------------

An earlier draft of this guide suggested adding one. That has been dropped:
it creates a user you did not ask for, and it buys little, because the
agent's only statement is the SELECT in part 14.5. If you later decide you
want the extra containment, a db_datareader login is the way to do it -- but
it is optional, and no longer part of this setup.

--------------------------------------------------------------------------------
  4.4  ON THE HRMS SIDE
--------------------------------------------------------------------------------

Nothing to create. Migration 0052 adds two tables and three columns to the
PostgreSQL database the HRMS already uses, as the role it already connects
as. The only new secret is BIOMETRIC_SYNC_TOKEN in hrms/.env, and each
environment gets its own.

  5.5  SELF-TEST -- DO NOT SKIP THIS

  AFTER THE TABLE LIST, --test PRINTS EVERY PUNCH RECORDED TODAY, grouped by
  employee, with a per-device tally:

      ----------------------------------------------------------------------
      TODAY'S PUNCHES  (2026-10-26)
      ----------------------------------------------------------------------
      158 punch(es) from 75 employee(s), newest 14:05:40

        9        Sunil More                1  10:14
        14       Sanjay Pragji Parmar      2  11:57, 11:58
        165      Abhiraj Das               2  09:15, 17:00
        ...

        per device:  device 1: 64   device 2: 93   device 21: 1
        A device missing from that list recorded nothing today.

  The row counts above it prove the tables hold history. This proves the
  devices are working NOW, which is the question you actually have standing
  at the server. Three things to read from it:

    * "NO PUNCHES AT ALL TODAY" before office hours is normal; during them it
      means the devices are not reaching eTimeTrackLite. That is a question
      for eTimeTrackLite, not for the agent -- the connection has already
      passed by this point.
    * A device missing from the per-device tally recorded nothing today,
      which is how a dead reader shows up.
    * A code shown as ?999 is a punch whose device user ID matches no
      employee in eTimeTrackLite. Rare, and worth chasing there.

    dbo.DeviceLogs IS NOT IN THAT LIST, and that is deliberate. It is a
  staging buffer eTimeTrackLite empties as it archives (3.1), so punches
  are read from the monthly tables only. What matters is the current
  month's table: it should have punches, with a date from today. If every
  table reads 0, see 12.3c; if the newest punch is days old, 12.3d.

  If the buffer is not empty you get an extra warning naming the count --
  harmless in itself, and 3.1 says when to act on it.

--------------------------------------------------------------------------------
  5.6  SCHEDULE IT -- EVERY 30 MINUTES
--------------------------------------------------------------------------------

Do this once --test passes and a manual push has worked (5.5, 6.5), not
before -- there is no point scheduling something you have not seen succeed
by hand.

Two values in the command below are specific to this machine, and getting
either wrong is the usual reason a task that works by hand fails on a
schedule. Find them first.

  (a) THE ACCOUNT -- the -User value
  ------------------------------------------------------------------
  It must be an account SQL Server already accepts, which means the one you
  ran --test successfully as. Ask Windows what that is:

      whoami

  On this installation that prints:

      win-5e3312pvo5j\administrator
      

  so the value to use is:

      -User "WIN-5E3312PVO5J\Administrator"

  That is COMPUTERNAME\username. Get the computer name on its own with:

      $env:COMPUTERNAME

  Do not invent a service account for this. The whole reason Windows
  Authentication works here (part 4.2) is that SQL Server already trusts
  this account; a new one would be refused until somebody granted it
  access, which is exactly the work this design avoids.

  With sql_auth = sql the Windows account does not matter to SQL Server,
  but it still has to be able to read C:\HRMS-Agent, so the same answer
  holds.

  (b) THE PYTHON -- the -Execute value
  ------------------------------------------------------------------
  THIS MACHINE HAS MORE THAN ONE PYTHON, AND ONLY ONE OF THEM HAS pyodbc.
  Running the agent as plain `py` gives:

      [FAIL] pyodbc is not installed.
             py -m pip install pyodbc

  while `py -3.10 essl_punch_agent.py --test` works. So py.exe on its own is
  the wrong thing to schedule: it would pick the default Python rather than
  the one the packages are in, and the task would fail every 30 minutes with
  that same line in the log.

  Ask the working Python where it lives:

      py -3.10 -c "import sys; print(sys.executable)"

  which prints something like:

      C:\Users\Administrator\AppData\Local\Programs\Python\Python310\python.exe

  Use that full path as -Execute. A full path also removes any dependence on
  PATH being set up for the task's account, which is a separate way this
  goes wrong.

  Confirm that interpreter really is the one with the packages:

      & "C:\Users\Administrator\AppData\Local\Programs\Python\Python310\python.exe" -c "import pyodbc, requests; print('both present')"

  Alternatively, install the packages into whichever Python `py` resolves to
  -- py -m pip install pyodbc requests -- and then py.exe is safe to
  schedule. One Python holding the packages is easier to keep straight than
  two.

  (c) CREATE THE TASK
  ------------------------------------------------------------------
  THE WORKING DIRECTORY DOES NOT MATTER. The agent finds essl_agent.ini, its
  state file and its log beside its own .py file, not in the current
  directory, so passing the script's full path is enough and -WorkingDirectory
  can be left out entirely. (An earlier version of this guide said the
  opposite. It was wrong.)

  There are three ways to tell the task who to run as. TRY THEM IN THIS
  ORDER -- the first needs no password at all, which is one less thing to
  break when somebody changes it later.

  ---- OPTION 1: run as SYSTEM (no password) -- TRY THIS FIRST ----------

  PowerShell as Administrator:

      $python = "C:\Users\Administrator\AppData\Local\Programs\Python\Python310\python.exe"
      $script = "C:\HRMS-Agent\essl_punch_agent.py"

      $action  = New-ScheduledTaskAction -Execute $python -Argument "`"$script`""

      $trigger = New-ScheduledTaskTrigger -Once -At (Get-Date).Date `
                   -RepetitionInterval (New-TimeSpan -Minutes 60) `
                   -RepetitionDuration ([TimeSpan]::MaxValue)

      $settings = New-ScheduledTaskSettingsSet `
                   -StartWhenAvailable `
                   -DontStopIfGoingOnBatteries `
                   -MultipleInstances IgnoreNew `
                   -ExecutionTimeLimit (New-TimeSpan -Hours 1)

      Register-ScheduledTask -TaskName "HRMS eSSL Punch Agent" `
        -Action $action -Trigger $trigger -Settings $settings `
        -User "SYSTEM" `
        -RunLevel Highest `
        -Description "Reads eSSL punches and pushes them to the HRMS."

  No -Password and no prompt: SYSTEM is a built-in account with no password
  to give. Nothing is stored, and a later password change cannot break the
  task.

  SQL Server then sees the login NT AUTHORITY\SYSTEM instead of your own
  account. A default SQL Express install grants SYSTEM access, so this
  usually just works -- but DO NOT ASSUME IT. Prove it with (d) below: the
  agent's own log says which login it connected as. If the log instead says

      Login failed for user 'NT AUTHORITY\SYSTEM'

  then SYSTEM is not accepted on this instance, and you want option 2 or 3,
  or sql_auth = sql (part 4.2) which makes the Windows account irrelevant to
  the database.

  ---- OPTION 2: your own account, still no password stored -------------

  S4U lets the task run as a named user without Windows holding their
  password. Same $action / $trigger / $settings as above, then:

      $principal = New-ScheduledTaskPrincipal `
                     -UserId "WIN-5E3312PVO5J\Administrator" `
                     -LogonType S4U -RunLevel Limited

      Register-ScheduledTask -TaskName "HRMS eSSL Punch Agent" `
        -Action $action -Trigger $trigger -Settings $settings `
        -Principal $principal `
        -Description "Reads eSSL punches and pushes them to the HRMS."

  SQL Server sees your own account, so whatever worked for --test still
  works. S4U needs the account to hold the "Log on as a batch job" right,
  which local administrators normally do.

  ---- OPTION 3: your own account with its password --------------------

  Only if the first two are refused. Same as option 2 but with
  -User / -Password:

      Register-ScheduledTask -TaskName "HRMS eSSL Punch Agent" `
        -Action $action -Trigger $trigger -Settings $settings `
        -User "WIN-5E3312PVO5J\Administrator" `
        -RunLevel Limited `
        -Description "Reads eSSL punches and pushes them to the HRMS." `
        -Password (Read-Host "Windows password for the task account" -AsSecureString)

  "The user name or password is incorrect" (0x8007052E) here is exactly what
  it says and has nothing to do with the rest of the command -- 12.13b.

  ---- WHY -RepetitionDuration IS NOT OPTIONAL -------------------------

  Without it some Windows versions refuse with:

      The RepetitionInterval and RepetitionDuration ... must be specified
      together.

  $trigger is then empty, and Register-ScheduledTask fails straight after
  with "Cannot validate argument on parameter 'Trigger'".
  [TimeSpan]::MaxValue means "repeat forever", which is what the agent
  wants.

  Each setting earns its place:

      -StartWhenAvailable           runs a missed cycle after a reboot
      -MultipleInstances IgnoreNew  a slow run never overlaps the next
      -ExecutionTimeLimit           a hung run is killed rather than wedging
                                    the task forever; the next one re-reads
                                    the same window, so nothing is lost

  IF THE POWERSHELL BLOCK STILL WILL NOT WORK, use schtasks.exe instead. It
  is present on every Windows, has no interval/duration pairing rule, and
  "/SC MINUTE /MO 30" means every 30 minutes indefinitely. /RU SYSTEM needs
  no password:

      schtasks /Create /TN "HRMS eSSL Punch Agent" /SC MINUTE /MO 30 /F /RL HIGHEST ^
        /TR "\"C:\Users\Administrator\AppData\Local\Programs\Python\Python310\python.exe\" \"C:\HRMS-Agent\essl_punch_agent.py\"" ^
        /RU SYSTEM

  (Those are cmd.exe continuations. In PowerShell put it on one line, or use
  a backtick instead of ^.) The inner quotes are escaped because both paths
  contain spaces. To use your own account instead, replace /RU SYSTEM with
  /RU "WIN-5E3312PVO5J\Administrator" /RP * -- the * makes it prompt rather
  than taking the password on the command line, where it would land in your
  shell history.

  Check what it created:

      schtasks /Query /TN "HRMS eSSL Punch Agent" /V /FO LIST

  PREFER THE GUI? Task Scheduler -> Create Task:

      General   name it; "Run whether user is logged on or not".
                "Change User or Group" -> type SYSTEM to avoid the password
                prompt entirely. "Run with highest privileges" is NOT needed
                for your own account.
      Triggers  New -> Daily, 12:00 AM; tick "Repeat task every" and type
                30 minutes; set "for a duration of" to Indefinitely
      Actions   Start a program
                  Program/script : the full python.exe path from (b)
                  Add arguments  : "C:\HRMS-Agent\essl_punch_agent.py"
                                   (with the quotes)
                  Start in       : leave EMPTY -- not needed
      Settings  tick "Run task as soon as possible after a scheduled start
                is missed"; "If the task is already running: Do not start a
                new instance"

  (d) PROVE THE SCHEDULER CAN RUN IT, NOT JUST YOU
  ------------------------------------------------------------------
      Start-ScheduledTask -TaskName "HRMS eSSL Punch Agent"
      Start-Sleep -Seconds 30
      Get-ScheduledTaskInfo -TaskName "HRMS eSSL Punch Agent" |
          Select-Object LastRunTime, LastTaskResult, NextRunTime
      Get-Content C:\HRMS-Agent\essl_agent.log -Tail 20

  LastTaskResult 0 is success. READ THE LOG, not just the exit code: running
  it by hand and having the scheduler run it are different things, and this
  is the step that proves the account, the interpreter and the working
  directory are all right. The log should end with something like:

      Target dev-pc: done -- 143 new punch(es), 71 day(s) created, 0 updated, 0 left alone.
      All targets up to date.

  If the log says "pyodbc is not installed", -Execute is pointing at the
  wrong Python -- go back to (b). If the log is empty, python.exe never
  started at all: the path or the working directory is wrong for that
  account (12.13).

--------------------------------------------------------------------------------
  5.7  FIREWALL
--------------------------------------------------------------------------------

  MUST BE OPEN
      Outbound TCP 443 from the Windows server to the HRMS (or 8000 to the
      PC in stage 1). Outbound HTTPS is nearly always already allowed, so in
      practice there is usually nothing to configure.

  MUST NOT BE OPENED
      SQL Server port 1433 to the internet or to network A. Nothing here
      needs it. (Stage 1's optional pull mode, 6.6, needs 1433 open to the
      LAN only -- close it again afterwards.)

      Any inbound port on the Windows server. The agent only makes outbound
      calls.

      Port 83 stays exactly as it is.

  IF OUTBOUND IS LOCKED DOWN, allow just the one destination:

      New-NetFirewallRule -DisplayName "HRMS punch push (outbound 443)" `
        -Direction Outbound -Action Allow -Protocol TCP `
        -RemoteAddress 103.195.81.148 -RemotePort 443 `
        -Program "C:\path\to\python.exe"

  ONE nginx NOTE FOR LARGE BACKFILLS. The HRMS nginx site already allows
  50 MB bodies (client_max_body_size 50M, see DEPLOYMENT.md step 11), and
  20000 punches is about 3 MB of JSON, so there is nothing to change. If you
  ever see HTTP 413, that is the setting to look at.

--------------------------------------------------------------------------------
  5.8  ON ENCRYPTION
--------------------------------------------------------------------------------

The token is a bearer secret: anyone holding it can write attendance. Over
HTTPS it is safe in transit. Over plain HTTP between two networks it is not
-- which is why verify_tls = no belongs only to stage 1, on a LAN, with a
throwaway token.

hrms\.env is created for you on first setup, pointing at a local SQLite file
with a throwaway biometric token. It is git-ignored. Never copy it to a
server; each server has its own.

  KEEP DB_ENGINE=sqlite IN THE PC's .env. Copying the Database section out
  of .env.example sets DB_ENGINE=postgres and points the PC at a database
  called hrms_prod_db with the password still "change-me". Start-up now
  stops with a message saying exactly that rather than something cryptic
  (12.18), but the fix is to leave the PC on sqlite. If you genuinely want
  PostgreSQL locally, requirements-dev-windows.txt already installs the
  driver, so you only need a local PostgreSQL and real credentials.

Part 15 has the rest of the VS Code detail.

--------------------------------------------------------------------------------
  6.2  LET THE WINDOWS SERVER REACH YOUR PC
--------------------------------------------------------------------------------

Find the PC's address on the network:

    ipconfig | findstr /i "IPv4"

Say it is 192.168.1.50. Three things have to be true, and missing any one of
them produces a different confusing error.

  (a) Django must listen on the network, not just on itself:

          py manage.py runserver 0.0.0.0:8000

      Plain `runserver` binds 127.0.0.1 only, and the Windows server would
      not be able to connect at all.

  (b) Django must accept that hostname. In hrms\.env:

          DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost,192.168.1.50

      Miss this and the push fails with "Invalid HTTP_HOST header", which
      looks like a networking problem and is not. Restart runserver after
      editing .env.

  (c) Windows Firewall on the PC must allow inbound 8000 from the LAN.
      PowerShell as Administrator:

          New-NetFirewallRule -DisplayName "HRMS dev server (LAN)" `
            -Direction Inbound -Action Allow -Protocol TCP `
            -LocalPort 8000 -RemoteAddress LocalSubnet

      -RemoteAddress LocalSubnet keeps it to your own network rather than
      opening the port generally. Remove it when stage 1 is finished:

          Remove-NetFirewallRule -DisplayName "HRMS dev server (LAN)"

  PART 9 -- MARK THE NIGHT-SHIFT EMPLOYEES
================================================================================
================================================================================

Do this on whichever environment you are testing, and again on production.

--------------------------------------------------------------------------------
  9.1  CHECK THE EMPLOYEE CODES LINE UP
--------------------------------------------------------------------------------

The HRMS matches a punch to a person in this order:

  1. the eSSL EmployeeCode against Employee.employee_code
  2. the device's UserId against Employee.biometric_device_user_id
  3. the device's UserId against Employee.employee_code
  4. any of the above ignoring case and leading zeros, so the device's
     "0014" finds employee code "14"

After the first push, open Attendance -> Biometric Sync. If "Punches
matching no employee" is empty, the codes line up and there is nothing to
do.

If it lists people, fix each one in whichever way is actually true:

  * the HRMS employee code is simply wrong
        -> correct it on the employee's form
  * the two codes are genuinely different, and both are right
        -> put the device's user ID in "Biometric Device User ID" on the
           employee's form

Nothing is lost while you work through the list. The punches are already
stored; the next run attaches every one of them and rebuilds those days.

--------------------------------------------------------------------------------
  9.2  TICK THE NIGHT-SHIFT EMPLOYEES
--------------------------------------------------------------------------------

Employees -> (employee) -> Edit -> Office Details -> Night Shift

Tick it for anyone whose duty crosses midnight. Their in-time then comes
from the day's last punch and their out-time from the next day's first
punch (2.2).

While you are on that screen: Weekly Off Day is often Saturday rather than
Sunday for night staff, and that is a separate setting next to it.

For someone who ROTATES between days and nights, do not tick it on the
employee. Use Attendance -> Shift Roster, where each entry carries its own
"Night shift" box. That is unambiguous whatever the shift is called and
whether or not its timings are filled in.

THE ADD FORM STARTS WITH THAT BOX TICKED, because the roster here is mainly
the night roster and ticking it every time is wasted work. THE OTHER SIDE OF
THAT: if you ever roster a DAY rotation, you must untick it. Left ticked, the
sync reads that rotation's in-time off the day's LAST punch instead of its
first, which looks like a sync fault and is not. Editing an existing entry
always shows what was saved, so nothing already in the roster changes.

The roster wins over the employee tick for every date it covers, and a roster
entry with ordinary daytime timings forces day-shift rules. Full precedence
in 2.4.

On this installation 16 employees show an overnight punch pattern, and it
clearly rotates -- Pavan Satrange on 117 nights, Vaibhav Jaiswal 64, Piyush
Aranjo 54, Zahid Ali 51, Sagar Belose 45, Samir Khan 44, Nirmal 33, Ramzan
Shaikh 23 and others. Those want roster entries, not employee ticks.

The Biometric Sync page lists everybody with the standing employee tick, so
that list can be eyeballed in one go. It does NOT list rostered nights,
which change week to week -- use the Shift Roster page for those.

--------------------------------------------------------------------------------
  9.3  RE-RUN THE DAYS YOU FIXED
--------------------------------------------------------------------------------

Attendance -> Biometric Sync -> "Rebuild from stored punches", with the
dates. It fetches nothing from the punch machine; it only re-applies the
rules to punches already held, so it is safe to press at any time.

Up to three months at a time from the page. For more, use the command in
10.2.


--------------------------------------------------------------------------------
  9.4  FINISHED ROTATIONS LEAVE THE ROSTER BY THEMSELVES
--------------------------------------------------------------------------------

Night duty rotates, so the Shift Roster fills up with entries whose dates
have gone by. A nightly job moves those out of the active list at 01:30, so
"who is on nights this week" stays readable. They appear under the roster's
Archived filter, and nothing is deleted.

  IT CHANGES NO ATTENDANCE. This is the part worth understanding, because
  the obvious implementation would get it wrong. An entry archived this way
  is flagged auto_archived, and the biometric sync keeps honouring
  auto-archived entries for the dates they covered. So when the two-hourly
  job re-reads the last few days -- or you press "Rebuild from stored
  punches" on something older -- an archived night rotation is still read as
  a night rotation.

  Without that distinction, tidying the roster would silently recompute old
  night shifts as day shifts: in-time taken from the morning punch instead
  of the evening one. The flag is separate from is_active precisely so that
  "its dates have passed" and "somebody decided it was wrong" stay different
  statements.

  THE GRACE PERIOD is 7 days by default, so a rotation that only just
  finished stays in the active list while the sync is still re-reading those
  dates. Change it in hrms/.env:

      SHIFT_ROSTER_ARCHIVE_AFTER_DAYS=7

  Keep it comfortably above BIOMETRIC_SYNC_LOOKBACK_DAYS (3).

  BY HAND, if you do not want to wait for 01:30:

      python manage.py archive_past_shift_assignments --dry-run
      python manage.py archive_past_shift_assignments
      python manage.py archive_past_shift_assignments --grace-days 30

  --dry-run lists what it would archive -- employee code, name, shift, dates
  and whether it was a night rotation -- and changes nothing.

  TO BRING ONE BACK, use the roster's Archived filter and restore it, the
  same as any other archived record.

    python manage.py sync_biometric_attendance \
        --from 2026-04-01 --to 2026-04-30

would leave the day alone. Read a few night-shift rows before running it for

went out against those numbers. They appear in the "left alone" count, and

rebuilding, that is a payroll decision, not a sync one.

--------------------------------------------------------------------------------

  Daily, ten seconds   The newest run is Success and today has punches.
  Weekly               "Matching no employee" is still zero.
  After onboarding     The new employee appears, with punches, within a day.
                       If not, their code does not match -- 9.1.
  After a device       Punch counts per day are back to normal.
  is replaced          A new device means new UserIds; check 9.1 again.

--------------------------------------------------------------------------------
  11.3  WHEN TO STOP UPLOADING THE EXCEL
--------------------------------------------------------------------------------

Not before you have compared a full week, employee by employee (8.8).

Until then, running both is safe: an Excel upload marks the days it touches
as manual, so the sync leaves them alone and the two cannot fight over the
same day. The cost is that those days will not follow the punch machine
afterwards either -- use --force (12.10) if you later want them rebuilt.

Once you do stop, nothing needs switching off. The upload page stays where
it is, for corrections and for any site the punch machine does not cover.

  12.1  --show-config did not find Settings.txt
  ---------------------------------------------
  Set essl_settings_file to its full path in essl_agent.ini. To find it:

      Get-ChildItem C:\ -Recurse -Filter Settings.txt -ErrorAction SilentlyContinue |
          Where-Object FullName -like "*iclock*" | Select-Object FullName

  Not fatal: fill in sql_server and sql_database by hand instead. Discovery
  only saves typing.

  12.2  ODBC driver 'ODBC Driver 17 for SQL Server' not installed
  ---------------------------------------------------------------
      py -c "import pyodbc; print(pyodbc.drivers())"

  Put the exact string it prints into sql_driver. If the list is empty, the
  MSI from 5.1(b) is not installed. With driver 18, note it encrypts by
  default -- the agent already allows for that with
  TrustServerCertificate=yes.

  12.3  Cannot read dbo.DeviceLogs: Login failed for user
  -------------------------------------------------------
  READ 12.3a FIRST. A wrong database name reports itself as a login
  failure, so this message is as often about sql_database as about the
  account.

  Once 12.3a is ruled out:

  With sql_auth = windows: SQL Server does not accept the Windows account
  you are running as. Check which that is:

      whoami

  Do not create a login for it. Either run as the account that does work
  (the one you use with SSMS), or switch to sql_auth = sql and reuse
  eTimeTrackLite's own `essl` login -- part 4.2.

  With sql_auth = sql: the password is wrong. Note that the sixth line of
  Settings.txt is NOT the password -- see 12.3b. Run
  eTimeTrackDatabaseSettings.exe to see what eTimeTrackLite is using.

  12.3a  "Cannot open database ... requested by the login. The login
         failed. (4060)"  -- almost always sql_database
  ----------------------------------------------------------------------
  Look at the name in the quotes. If it is a SERVER or INSTANCE name --
  something like WIN-5E3312PVO5J\SQLEXPRESS -- then sql_database has a
  server name in it, and the "Login failed (18456)" printed alongside is a
  CONSEQUENCE of that, not a separate problem. The account is probably
  fine.

  sql_database is the name of a database INSIDE SQL Server. Here:

      sql_database = eTimetracklite1

  or leave it blank and let the agent read it from eTimeTrackLite's own
  Settings.txt, which is always right:

      sql_database =

  Then:

      py essl_punch_agent.py --show-config

  The agent now refuses to start on this rather than letting SQL Server
  answer confusingly, so a current version tells you directly. The ini
  shipped with older versions of this guide listed two `sql_server`
  examples just above the blank sql_server and sql_database lines, which
  invited exactly this; part 14.1 no longer does.

  12.3b  Pasting the sixth line of Settings.txt as sql_password
  -------------------------------------------------------------
  The sixth line looks like a password (something like "rKWYgQrTCGc=") but
  it is encrypted with a key inside eTimeTrackLiteLibrary.dll. Using it
  produces a plain "Login failed", which looks like the account is wrong.

  Either get the real password from eTimeTrackDatabaseSettings.exe, which
  ships beside eTimeTrackLite, or avoid the question entirely:

      sql_auth = windows
      sql_password =

  The agent recognises that specific value and stops with this explanation.

  12.3c  --test connects fine but reports 0 punches
  -------------------------------------------------
  If it also says "No punches anywhere in the last 12 months", the
  connection and the credentials are right and this is eTimeTrackLite's
  data, not the agent.

  First rule out the version problem: a current agent lists the tables it
  read, like

         DeviceLogs                      0
         DeviceLogs_10_2026          14201  2026-10-01 .. 2026-10-26

  An agent that reads only dbo.DeviceLogs reports a healthy connection and
  0 punches on this installation, because that table is a buffer and is
  normally empty (3.1). If --test shows no per-table breakdown, the agent
  on the Windows server is an older copy -- re-copy essl_punch_agent.py
  from the repository (5.2).

  With a current agent still showing nothing, check in eTimeTrackLite
  itself that the devices are downloading. To see where the punches are, in
  SSMS:

      SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
      WHERE TABLE_SCHEMA = 'dbo'
        AND (TABLE_NAME = 'DeviceLogs' OR TABLE_NAME LIKE 'DeviceLogs[_]%')
      ORDER BY TABLE_NAME;

      SELECT COUNT(*) AS punches, MIN(LogDate), MAX(LogDate)
      FROM dbo.DeviceLogs_10_2026;        -- this month's table

  A row count of 0 in every table means eTimeTrackLite has not collected
  anything, which is a question for eTimeTrackLite, not for this
  integration.

  12.3d  "The newest punch is N days old"
  ---------------------------------------
  The agent found punches but nothing recent. It will still send what is
  there. This usually means eTimeTrackLite has stopped collecting from the
  devices -- a device offline, or its scheduled download not running. Check
  that in eTimeTrackLite; the agent only reads what eSSL has already
  gathered.

  12.4  Cannot read dbo.DeviceLogs: server was not found
  ------------------------------------------------------
  The instance name is wrong, or SQL Browser is not running. Let
  --show-config tell you what Settings.txt says, then try in sql_server, in
  this order:

      .\SQLEXPRESS
      localhost\SQLEXPRESS
      WIN-5E3312PVO5J\SQLEXPRESS

  Confirm the service is up:

      Get-Service | Where-Object Name -like "MSSQL*"

  12.5  A target says HTTP 401
  ----------------------------
  That server's token does not match. It must be byte-for-byte identical in
  essl_agent.ini (token) and that server's hrms/.env
  (BIOMETRIC_SYNC_TOKEN). Usual causes: a trailing space; quotes added
  around the value in .env (do not quote it); the service not restarted
  after editing .env.

  Each environment has its own token. A 401 right after a stage change
  usually means the previous stage's token is still in the ini.

      # on the HRMS
      grep BIOMETRIC_SYNC_TOKEN hrms/.env
      sudo systemctl restart hrms-prod-gunicorn

  12.6  A target says HTTP 404
  ----------------------------
  The HRMS at that URL does not have the endpoint -- the code is not
  deployed there, or gunicorn was not restarted. Check from that server:

      curl -s -o /dev/null -w "%{http_code}\n" \
           https://.../api/biometric/status/      # want 401, not 404

  12.7  A target says HTTP 400, or "Invalid HTTP_HOST header"
  -----------------------------------------------------------
  The agent sees this as:

      400 Client Error: Bad Request for url: http://192.168.1.86:8000/...

  which is NOT a token problem, however much it looks like one next to the
  401 case. Django rejected the request before any view ran, because the
  host in the agent's url is not in that server's DJANGO_ALLOWED_HOSTS.

  Stage 1, almost always. In the PC's hrms\.env:

      DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost,192.168.1.86

  using the PC's own LAN address (ipconfig | findstr /i "IPv4"), then
  restart runserver -- .env is read at start-up.

  Two more things have to be true in stage 1, and each fails differently:
  Django must be started as `runserver 0.0.0.0:8000` (plain runserver binds
  127.0.0.1 only, and the agent cannot connect at all), and the PC's
  firewall must allow inbound 8000 from the LAN. All three are in 6.2.

  On a server it is the same cause -- the hostname in the agent's url is not
  in that server's DJANGO_ALLOWED_HOSTS. Restart gunicorn after editing.

  A current agent prints this explanation itself, in --test and in the
  scheduled run's log.

  12.8  A target times out or cannot resolve
  ------------------------------------------
  Network, not HRMS. From the Windows server:

      Test-NetConnection -ComputerName hrms.zacoinfotech.com -Port 443
      try { Invoke-WebRequest https://hrms.zacoinfotech.com/api/biometric/status/ }
      catch { $_.Exception.Response.StatusCode.value__ }

  A certificate error ("CERTIFICATE_VERIFY_FAILED") means the HTTPS
  certificate is self-signed or the hostname does not match. Fix the
  certificate; verify_tls = no is a stopgap, not a fix.

  12.9  One target fails and the others are fine
  ----------------------------------------------
  That is the intended behaviour -- nothing to fix beyond that one target.
  It is skipped, retried next run, and its resume point has not moved, so
  the punches it missed are sent again. The agent exits 1 so the Scheduled
  Task shows the failure, while the healthy targets stayed up to date.

  12.10  Punches arrive but attendance does not change
  ----------------------------------------------------
  Look at the "left alone" column on the Biometric Sync page, then at the
  day itself. One of these will be true:

    * The day has manual times -- an Excel upload or an approved
      correction. That is the design (2.5). To let the machine win anyway:

          python manage.py sync_biometric_attendance \
              --from 2026-10-01 --to 2026-10-31 --force

      --force rebuilds those days from the punches alone, ignoring the times
      already there, and still refuses to touch finalized payroll periods.

    * The day is inside a finalized payroll run -- 10.3.
    * The day is before the employee's date of joining.
    * The employee's status is Left or Archived.

  12.11  A night-shift employee's day looks wrong
  -----------------------------------------------
  In this order:

    1. Is "Night Shift" ticked? The Biometric Sync page lists who is.
    2. Is there a Shift Roster entry covering that date? It overrides the
       tick, and a daytime entry forces day-shift rules.
    3. Did they actually punch? Dry-run that one person:

          python manage.py sync_biometric_attendance \
              --from 2026-10-23 --to 2026-10-24 \
              --employee ZCPL001 --dry-run

       It prints the punches, how the day is classified (day/night) and what
       the rules give.
    4. A lone morning punch gives no in-time, on purpose: that punch is the
       previous night's out-punch (BIOMETRIC_NIGHT_IN_FROM, 2.3).

  12.12  The out-time is blank although they punched out
  ------------------------------------------------------
  The span exceeded BIOMETRIC_MAX_SHIFT_HOURS (16), so it was treated as a
  missed out-punch rather than credited. Usually that is true: somebody
  forgot to punch out and the next morning's punch got picked up. If your
  shifts are genuinely longer, raise the setting and restart.

  12.13  Reading LastTaskResult
  -----------------------------
  Not every non-zero value is a failure:

      0        success
      267009   0x00041301 -- THE TASK IS STILL RUNNING. Not an error. A
               first run reads up to first_run_days of history and pushes it
               in batches, so 30 seconds is often not long enough. Wait and
               query again.
      267011   0x00041303 -- the task has never run
      1        0x1 -- the script ran and reported failure; read on

  When it really is 0x1, the log says why:
  The script ran and reported failure. The log says why:

      Get-Content C:\HRMS-Agent\essl_agent.log -Tail 40

  Two causes account for nearly all of these:

    * The log ends with "pyodbc is not installed". -Execute is pointing at a
      Python that does not have the packages. This machine has more than one
      Python and only one has pyodbc, so py.exe on its own is not safe to
      schedule -- 5.6(b) finds the right full path.

    * The log is EMPTY. python.exe never started at all, so -Execute or the
      script path is wrong for that account -- both come from 5.6. Note the
      working directory is NOT the problem: the agent finds its ini, state
      file and log beside its own .py file, so only the script path has to
      be right.

  To see exactly what the scheduler is running:

      (Get-ScheduledTask -TaskName "HRMS eSSL Punch Agent").Actions |
          Select-Object Execute, Arguments, WorkingDirectory

  12.13a  "The RepetitionInterval and RepetitionDuration ... must be
          specified together", then "Cannot validate argument on
          parameter 'Trigger'"
  ----------------------------------------------------------------------
  Two errors, one cause. The first means the trigger was never built, so
  $trigger is empty; the second is Register-ScheduledTask refusing that
  empty variable a moment later. Fixing the first fixes both.

  Add -RepetitionDuration, as 5.6(c) now does:

      $trigger = New-ScheduledTaskTrigger -Once -At (Get-Date).Date `
                   -RepetitionInterval (New-TimeSpan -Minutes 30) `
                   -RepetitionDuration ([TimeSpan]::MaxValue)

  Some Windows versions accept -RepetitionInterval on its own and some
  insist on the pair, which is why an earlier version of this guide worked
  on one machine and not another.

  IF THE ERROR DETAIL MENTIONS New-JobTrigger OR
  Microsoft.PowerShell.ScheduledJob.NewJobTriggerCommand, something else is
  going on: the name resolved to New-JobTrigger from the PSScheduledJob
  module, which is a different cmdlet for a different feature and builds an
  object Register-ScheduledTask cannot use. Force the right module:

      $trigger = ScheduledTasks\New-ScheduledTaskTrigger -Once `
                   -At (Get-Date).Date `
                   -RepetitionInterval (New-TimeSpan -Minutes 30) `
                   -RepetitionDuration ([TimeSpan]::MaxValue)

  Check which one you are actually getting with:

      Get-Command New-ScheduledTaskTrigger | Select-Object Source, CommandType

  It should say ScheduledTasks. If it does not, or if any of this keeps
  fighting you, skip the cmdlets entirely and use the schtasks.exe form in
  5.6(c) -- it has none of these quirks.

  12.13b  "The user name or password is incorrect" (0x8007052E) when
          registering the task
  ----------------------------------------------------------------------
  The task definition is fine -- this is Windows refusing the account and
  password pair, and nothing else in the command is at fault. The quickest
  answer is usually to stop supplying a password at all: use option 1
  (SYSTEM) or option 2 (S4U) in 5.6(c).

  If you want option 3 to work, the causes in order of likelihood:

    * THE PASSWORD IS WRONG. It is typed blind. Check it without changing
      anything:

          Add-Type -AssemblyName System.DirectoryServices.AccountManagement
          $ctx = New-Object System.DirectoryServices.AccountManagement.PrincipalContext(
                     'Machine', $env:COMPUTERNAME)
          $sec = Read-Host "password" -AsSecureString
          $ctx.ValidateCredentials('Administrator',
              [Runtime.InteropServices.Marshal]::PtrToStringAuto(
                  [Runtime.InteropServices.Marshal]::SecureStringToBSTR($sec)))

      True means the password is right and the problem is elsewhere. False
      means it is simply wrong.

    * THE ACCOUNT HAS A BLANK PASSWORD. Task Scheduler cannot store one for
      a task that runs when nobody is logged in, and the local policy
      "Accounts: Limit local account use of blank passwords to console logon
      only" blocks it outright. Either give the account a password or use
      SYSTEM.

    * THE USER NAME IS NOT WHAT YOU THINK. Confirm both halves rather than
      typing them from memory:

          whoami
          $env:COMPUTERNAME
          Get-LocalUser | Select-Object Name, Enabled

      It must be COMPUTERNAME\username for a local account. A domain account
      is DOMAIN\username, and the domain controller has to be reachable at
      registration time.

    * THE ACCOUNT IS A MICROSOFT ACCOUNT. Those cannot be used this way.
      Use SYSTEM or a local account.

  Note the task is NOT created when this fails, so there is nothing to clean
  up before trying again:

      Get-ScheduledTask -TaskName "HRMS eSSL Punch Agent" -ErrorAction SilentlyContinue

  12.14  Nothing has synced for days and nobody noticed
  -----------------------------------------------------
  Both halves report, so check both:

      HRMS     Attendance -> Biometric Sync -> Recent sync runs
               sudo journalctl -u hrms-prod-celery -n 100 --no-pager | grep -i biometric
               systemctl is-active hrms-prod-celery hrms-prod-celerybeat

      Windows  Get-Content C:\HRMS-Agent\essl_agent.log -Tail 40
               Get-ScheduledTaskInfo -TaskName "HRMS eSSL Punch Agent"

  A long gap costs nothing permanent: the agent resumes from where it left
  off, however long ago, and the stored punches rebuild the attendance.

  12.15  Staging seems to be changing production data
  ---------------------------------------------------
  Stop staging's Celery immediately:

      sudo systemctl stop hrms-staging-celery hrms-staging-celerybeat

  Then check 7.1: almost certainly the two share a Redis database number, so
  one project's workers are picking up the other's tasks.

      grep -h CELERY_BROKER_URL /home/multihost/hrms_staging/hrms/.env \
                                /home/multihost/hrms_prod/hrms/.env

  The numbers at the end must differ. Fix staging's .env, then start its
  services again.

  12.16  Attendance appeared for a date before someone joined
  -----------------------------------------------------------
  It should not -- that day is skipped. If you see it, the employee's Date
  of Joining is blank or wrong on that record. Fix it, then rebuild those
  dates (9.3).

  12.17  The scheduled HRMS job never runs
  ----------------------------------------
      systemctl is-active hrms-prod-celerybeat hrms-prod-celery

  Both must be active. Beat reads the schedule at start-up, so if you
  changed BIOMETRIC_SYNC_HOURS without restarting beat, the old schedule is
  still in force. Also confirm CELERY_BROKER_URL uses a Redis database no
  other project uses.

  12.18  "Error loading psycopg2 or psycopg module"
  -------------------------------------------------
  DB_ENGINE=postgres, but no PostgreSQL driver is installed in that
  environment. Almost always a development PC whose .env had the Database
  section pasted in from .env.example.

  The project now answers this itself -- start-up stops with the two ways
  out rather than just the module name -- but for reference:

      On a PC, you want SQLite. In hrms\.env:
          DB_ENGINE=sqlite

      If you really do want PostgreSQL locally:
          pip install "psycopg[binary]"
      requirements-dev-windows.txt already includes it, so a PC set up from
      that file will not hit this at all.

      On a server this should be impossible, because
      pip install -r hrms/requirements.txt includes psycopg. Seeing it there
      means the venv is not the one systemd is using, or pip install was
      skipped during the deploy.

  Related messages from the same checks, all of which name the exact
  variable rather than failing later with a KeyError or an authentication
  error:

      "DB_ENGINE=postgres needs DB_NAME, which is not set in hrms/.env"
      "DB_PASSWORD in hrms/.env is still the placeholder 'change-me'"
      "DB_ENGINE='mysql' ... is not a value this project understands"


  12.19  A rostered night shift is being treated as a day shift
  --------------------------------------------------------------
  The symptom: an employee you rostered onto nights gets an in-time from the
  MORNING punch instead of the evening one, and often no out-time at all.

  SINCE THE ADD FORM NOW STARTS TICKED (9.2), the commoner complaint is the
  opposite one -- see 12.19a. Check that first if the employee is on days.

  Almost always the roster entry says nothing the sync can act on -- no
  "Night shift" tick, no timings, and a name like "B Shift" or "Shift 3"
  that carries no hint either way (2.4). Open the entry in Attendance ->
  Shift Roster and tick Night shift.

  To see which entries are in that state, on the HRMS:

      python manage.py shell -c "
      from website.models import ShiftAssignment
      for a in ShiftAssignment.objects.filter(is_active=True).select_related('employee'):
          if a.is_night_shift: continue
          if a.shift_start_time and a.shift_end_time: continue
          if any(h in (a.shift_name or '').lower()
                 for h in ('night','overnight','graveyard','nite')): continue
          print(a.employee.employee_code, a.employee, a.shift_name,
                a.start_date, a.end_date)
      "

  Anything printed is an entry the sync cannot classify, so those dates fall
  back to the employee's own Night Shift tick. That is correct for somebody
  permanently on nights and wrong for a rotation -- tick the entry.

  Then rebuild those dates: Attendance -> Biometric Sync -> "Rebuild from
  stored punches". Nothing is re-fetched; the rules are simply re-applied to
  punches already held.

  Two other causes worth ruling out:

    * THE ENTRY IS ARCHIVED. Archived entries (is_active off) are ignored
      completely, so the employee falls back to their own setting.

    * THE DATES DO NOT COVER THE DAY. A night shift that starts on 23 Oct
      needs 23 Oct inside start_date..end_date. The out-time comes from
      24 Oct's punches, but it is the START date that has to be rostered.


  12.19a  A DAY rotation is being treated as a night shift
  --------------------------------------------------------
  The symptom: a day-shift employee's in-time is their LAST punch of the day
  rather than their first, and the out-time comes from the following
  morning. Hours and status then look nonsensical.

  Cause: the Shift Roster's add form starts with "Night shift" ticked (9.2,
  and it is deliberate -- the roster here is mainly the night roster), and
  the entry for a day rotation was saved without unticking it.

  Open the entry in Attendance -> Shift Roster and untick it. To find every
  entry it applies to:

      python manage.py shell -c "
      from website.models import ShiftAssignment
      for a in ShiftAssignment.objects.filter(is_active=True, is_night_shift=True
                                              ).select_related('employee'):
          print(a.employee.employee_code, a.employee, '|', a.shift_name, '|',
                a.start_date, a.end_date, '|',
                a.shift_start_time, a.shift_end_time)
      "

  Read that list against who actually works nights. An entry ticked for
  nights whose timings are plainly daytime (09:00-18:00) is the giveaway.

  Then rebuild those dates: Attendance -> Biometric Sync -> "Rebuild from
  stored punches". Nothing is re-fetched.

--------------------------------------------------------------------------------
  13.2  DATABASE OBJECTS
--------------------------------------------------------------------------------

  On the HRMS. Nothing is created on the eSSL side.

    website_biometricpunch
        One row per punch, as the device recorded it. Unique on
        (device_user_id, punch_date, punch_time) -- the same identity eSSL
        itself uses (3.3) -- which is what makes re-sending free. Never
        rewritten.

    website_biometricsyncrun
        One row per sync attempt, with its counters, so the page can show
        whether the automation is running.

    website_employee.is_night_shift              bool, default false
    website_employee.biometric_device_user_id    nullable
    website_attendance.times_locked              bool, default false

  Punch times are stored as a local date plus a local time, exactly as the
  device recorded them -- not as an aware datetime. That is deliberate: it
  is what Attendance.in_time and out_time already are, so no timezone
  conversion exists anywhere, and a 23:50 punch can never drift onto the
  wrong day.

--------------------------------------------------------------------------------
  13.3  ENDPOINTS
--------------------------------------------------------------------------------

  POST /api/biometric/punches/        header X-HRMS-Sync-Token

      {"device": "<agent name>", "punches": [ {...}, ... ]}

      punch fields: device_user_id, employee_code, employee_name,
                    punch_date ("YYYY-MM-DD"), punch_time ("HH:MM:SS"),
                    device_id, direction, source_log_id

      Only device_user_id, punch_date and punch_time are required; the rest
      make the audit trail readable.

      -> {"ok": true, "run_id": n, "received": n, "stored": n,
          "unmatched": n, "attendance_created": n, "attendance_updated": n,
          "attendance_skipped": n, "message": "..."}

      At most 20000 punches per request. Punches already held are ignored,
      so re-sending an overlapping window is free.

  GET  /api/biometric/status/         header X-HRMS-Sync-Token

      -> {"ok": true, "server_date": "...", "latest_punch_date": "...",
          "lookback_days": n, "last_run": {...}}

      This is how the agent works out where to resume when it has lost its
      own state file.

  Both answer 401 for a missing, wrong, or unconfigured token, and say
  nothing about which. They carry no session and no CSRF token by design --
  the caller is a scheduled script on another network, not a browser.

  GET  /attendance/biometric-sync/          the page (login + permission)
  POST /attendance/biometric-sync/rebuild/  the Rebuild button

--------------------------------------------------------------------------------
  13.4  SETTINGS
--------------------------------------------------------------------------------

  In each environment's own hrms/.env. Complete block in part 14.2.

    BIOMETRIC_SYNC_TOKEN           required; empty switches the feed off
    BIOMETRIC_SYNC_LOOKBACK_DAYS   3      days each run re-reads (min 2)
    BIOMETRIC_SYNC_HOURS           10,12,14,16,18,20,22,0

--------------------------------------------------------------------------------
  14.5  THE SQL THAT RUNS AGAINST eTimeTrackLite
--------------------------------------------------------------------------------

Only SELECTs. Nothing in eTimeTrackLite is written to or changed.

First the agent asks which punch tables exist, because the monthly ones come
and go (3.1):

    SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
    WHERE TABLE_SCHEMA = 'dbo' AND TABLE_TYPE = 'BASE TABLE'
      AND (TABLE_NAME = 'DeviceLogs' OR TABLE_NAME LIKE 'DeviceLogs[_]%');

It keeps the DeviceLogs_<month>_<year> tables covering the window, discards
anything else the server reported, and reads them as one result. For a
window inside October 2026 that is:

    SELECT  p.UserId,
            e.EmployeeCode,
            e.EmployeeName,
            p.LogDate,
            p.DeviceId,
            p.PunchDirection,
            p.DeviceLogId
    FROM    (
        SELECT  l.UserId, l.LogDate, l.DeviceId,
                COALESCE(l.Direction, l.AttDirection) AS PunchDirection,
                l.DeviceLogId
        FROM    dbo.[DeviceLogs_10_2026] AS l
        WHERE   l.LogDate >= @since AND l.LogDate < @until
    ) AS p
    LEFT JOIN dbo.Employees AS e ON e.EmployeeCodeInDevice = p.UserId
    ORDER BY p.LogDate, p.UserId;

A longer window simply adds a UNION ALL branch per month: October to
December 2026 gives three. Table names are never built from anything but
what INFORMATION_SCHEMA returned, re-checked against the pattern DeviceLogs
or DeviceLogs_<digits>_<digits>, and bracket-quoted.

With read_devicelogs_buffer = yes, a dbo.[DeviceLogs] branch is added ahead
of the monthly ones. Either way one more statement runs each time, purely to
notice a buffer that is not being emptied (3.1):

    SELECT COUNT(*) FROM dbo.DeviceLogs;

--test additionally runs these three, purely to report:

    SELECT COUNT(*), MAX(LogDate), MIN(LogDate) FROM dbo.DeviceLogs;
    SELECT COUNT(*) FROM dbo.Employees WHERE RecordStatus = 1;
    SELECT SUSER_NAME(), DB_NAME();

Part 3 explains why dbo.DeviceLogs and not dbo.AttendanceLogs, why the join
is a LEFT join, and why the archive tables are not read.

--------------------------------------------------------------------------------
  14.6  REMOVING IT ALL AGAIN
--------------------------------------------------------------------------------

  STOP THE FEED, KEEP EVERYTHING  (the gentlest step, and reversible)

      On the Windows server:
          Disable-ScheduledTask -TaskName "HRMS eSSL Punch Agent"

      Punches stop arriving. Attendance already written stays. Re-enable
      with Enable-ScheduledTask and the agent resumes from where it stopped.

  STOP THE HRMS SIDE ONLY

      In hrms/.env set BIOMETRIC_SYNC_TOKEN= (empty), then restart gunicorn.
      The endpoint refuses everything and the agent's pushes 401. The
      two-hourly job still runs but has nothing new to work with.

  REMOVE THE STAGING PROJECT

      sudo systemctl disable --now hrms-staging-gunicorn \
                                   hrms-staging-celery \
                                   hrms-staging-celerybeat
      sudo rm /etc/systemd/system/hrms-staging-*.service
      sudo systemctl daemon-reload
      sudo rm -f /etc/nginx/sites-enabled/hrms_staging
      sudo rm -f /etc/nginx/sites-available/hrms_staging
      sudo nginx -t && sudo systemctl reload nginx
      sudo -u postgres dropdb hrms_staging_db
      sudo -u postgres dropuser hrms_staging_user
      rm -rf /home/multihost/hrms_staging

      Also delete the DNS record and, if you created one, revoke the
      staging certificate:
          sudo certbot delete --cert-name staging.zacoinfotech.com

      Then set [hrms:ubuntu-staging] enabled = no in essl_agent.ini.

  REMOVE THE AGENT FROM THE WINDOWS SERVER

      Unregister-ScheduledTask -TaskName "HRMS eSSL Punch Agent" -Confirm:$false
      Remove-Item -Recurse C:\HRMS-Agent

      Nothing in eTimeTrackLite or SQL Server was ever changed, so there is
      nothing to undo there.

  REVERSE THE DATABASE CHANGE  (last resort -- this deletes the punches)

      python manage.py migrate website 0051

      This drops website_biometricpunch and website_biometricsyncrun and
      removes the three columns. Attendance in/out times already written
      STAY -- they are ordinary Attendance rows now. What you lose is the
      punch history, so the rules could not be re-applied afterwards.

      Take a backup first. Prefer the "stop the feed" options above unless
      you are certain.
